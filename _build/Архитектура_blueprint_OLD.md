# Думающий Клод — Архитектура (ИСТОРИЧЕСКАЯ ВЕРСИЯ)

> **Устарело.** Актуальный источник архитектуры — [`../ARCHITECTURE.md`](../ARCHITECTURE.md). Этот файл — снимок до релиза-вычитания 2026-06-28 (описывает 18 скиллов, часть уже в кладбище `_build/graveyard/`). Оставлен для истории, в живые ссылки не входит.

Документ, чтобы (а) через год освежить в памяти, как всё устроено и зачем, и (б) дать постороннему — например разработчику — честно оценить работу. Без воды: что это, как устроено, как проверялось, где слабые места.

## 1. Что это

Слой управления контекстом (context-engineering harness) поверх Claude. Идея простая: ценность не в «более умной модели», а в **дисциплине процесса** вокруг задачи. Сам интеллект уже есть в Claude — система лишь организует, *что* и *в каком порядке* в него попадает.

Это **не отдельная модель** и **не reasoning-модель** в техническом смысле (как o1/R1). Это набор инструкций + модулей, работающий поверх любой версии Claude.

## 2. Форма (как собрано)

Три слоя:
1. **Ядро** (`CLAUDE.md`) — всегда-активные принципы и роутер. «Конституция».
2. **Скиллы** (18 модулей) — процедурные режимы, подключаются по необходимости.
3. **Субагенты** — изолированные контексты для параллельного рисёрча и критики.

Ключевое архитектурное правило — **single-writer**: решает и пишет результат всегда один поток; субагенты только читают, исследуют, критикуют. (Вывод из спора двух подходов: Anthropic показала +90% качества на мульти-агентном рисёрче, но Cognition показала, что мульти-агент ломает контекст. Компромисс: один «писатель» + рой «читателей-критиков».)

## 3. Принципы ядра

1. **Не выдумывать.** Не найдено — сказать прямо. Метки типа знания: `[Факт]` (с источником) · `[Вывод]` (из посылок) · `[Предположение]` · `[Не найдено]`.
2. **Честность важнее покладистости.** Если пользователь не прав — спорить аргументами, а не поддакивать.
3. **Value-gate.** Не подключать модуль/рисёрч/роль без реальной пользы. Гейт — молчаливый (не проговаривать «модуль не нужен»).
4. **Не хардкодить количество** (ролей, сфер, вариантов) — определять по «эффект × усилия».
5. **Классифицируй, потом маршрутизируй** — распознавать тип задачи на лету, без закрытых списков.
6. **Single-writer** (см. выше).
7. **Гейт перед исполнением** — план показывается на одобрение до создания/изменения чего-либо.
8. **Verifier-first** — потолок качества задаётся тем, насколько результат можно проверить. Есть проверка → гнать качество перебором; нет → выдавать помеченные гипотезы.
9. **Гипотеза — ставка, не факт.** Важные предположения логируются с предсказанием и проверяются практикой; со временем → факт, правка или удаление.
10. **Минимально достаточный контекст, observability, обратимость** — каждому шагу только нужное; ключевые решения фиксируются в журнал; необратимое — через подтверждение.

## 4. Процесс (для сложных задач)

`Роутер (классификация + value-gate)` → `Цели и Definition of Done` → `План + пре-мортем` → 🚪 `Гейт одобрения` → `Исполнение (single-writer)` → `Критика (red-team)` → `Верификация против DoD` → `Ретроспектива в память`.

Гейт одобрения человеком стоит **между планом и исполнением**: исследование и планирование дёшевы (пусть идут свободно), но перед созданием/изменением — показать план.

## 5. Каталог модулей (18 скиллов)

| Модуль | Что делает |
|---|---|
| architect | Размытую/большую задачу → цель, Definition of Done, план, гейт |
| prompt-builder | Сырой запрос → полноценный промпт (роль, контекст, критерии, few-shot) |
| roles | Несколько экспертных точек зрения. NB: помогает идеям/дизайну, не фактам |
| red-team | Критика: скептик/оппонент/безопасник/конкурент; сначала стилман |
| adjacent-fields | Переносит рабочие принципы/механизмы из смежных сфер |
| landscape | Анализ конкурентов / топ-N, сбор сильнейшего в одно |
| benchmark | Подбор эталона и сверка с планкой (узкий триггер — неочевидный эталон) |
| alternatives | 3–4 реально разных варианта + превью для дизайна |
| divergent | Брейнсторм: широкое расхождение → отбор лучшего |
| memory | Файловая память между сессиями + реестр гипотез |
| verification | Гейт Definition-of-Done: подтверждение готовности (для кода — тесты) |
| pre-mortem | «Представь, что провалилось — почему?» до старта |
| steelman | Сильнейшая версия идеи перед критикой |
| prioritization | Эффект×усилия → порядок (условный keep, узкая ниша) |
| fact-mode | Против галлюцинаций: источники, само-проверка, метки, «не нашёл» |
| amplifier | Вскрывает зарытые допущения/дефекты в готовом артефакте |
| discovery | Генератор+верификатор+эволюция; без верификатора — помеченные гипотезы |
| overseer | Надзор «со стороны» за процессом + еженедельное авто-ревью системы |

(Модуль «прояснение/коммуникация» встроен в ядро `CLAUDE.md`; «выбор модели» — конфиг: Sonnet для рутины, Opus для тяжёлого суждения.)

## 7. Развёртывание

- **Cowork** (дом для бизнес-задач): `CLAUDE.md` → инструкции проекта; плагин `reasoning-harness` → Customize → Plugins → Add marketplace.
- **Claude Code** (разработка): `CLAUDE.md` → корень репозитория; плагин или скиллы в `.claude/skills/`.
- **Любой чат**: вставить `portable-system-prompt.md` первым сообщением (только ядро, без скиллов/памяти).

## 8. Как это проверялось (главное для честной оценки)

Система не принята «на веру» — каждый модуль прошёл проверку:
1. **A/B-тест** (`/test-module`): одна задача решается дважды — без модуля (A) и с модулем (B) — на 2–3 кейсах, включая «ловушку», где модуль должен сам отказаться (value-gate).
2. **Независимый судья.** Вердикт выносит *отдельная* сессия Claude (Opus), которая модули не строила — чтобы убрать предвзятость автора. (Это реально сработало: судья оказался строже автора, дважды ставил drop-кандидат.)
3. **Реестр гипотез** копит вердикты; решения keep/tweak/drop вносятся в систему.

**Результат:** все 18 модулей оставлены (KEEP), часть — с суженными триггерами. Главный честный вывод: многие модули **частично дублируют то, что базовая модель делает сама**; реальная ценность — там, где модуль **ловит то, что база упускает** (например `fact-mode` поймал сфабрикованные ссылки, `amplifier` — скрытое допущение, ломающее запуск). Поэтому триггеры узкие, а не «включать всё подряд».

## 9. Честные ограничения (для критики)

- **Тесты неглубокие:** n=3 на модуль, оценка по сводкам A/B, а не по сырым транскриптам. Это гейт «keep/drop», а не строгое измерение.
- **Само-активация базы** конфаундит сравнение: «без модуля» Claude часто уже частично делает то же — поэтому ценность ряда модулей это *enforcement/консистентность*, а не новое поведение.
- **«Весь интеллект уже в Claude»** — система не повышает потолок рассуждений модели, только дисциплинирует процесс.
- **Память файловая**, не «магическая»: работает ровно настолько, насколько ассистент читает/пишет её по инструкции.
- **Маржинальные модули:** `prioritization` — условный keep; `benchmark`, `amplifier` держатся на узких триггерах; открытый вопрос — пересечение `amplifier` с `pre-mortem`/`red-team`.
- **Риск переусложнения:** 18 модулей легко превратить в оверхед; защита — value-gate и молчаливые гейты, но это требует дисциплины.
- **Overseer не «живёт сам»:** нет фонового процесса; он срабатывает на чекпойнтах и по расписанию (еженедельно).
