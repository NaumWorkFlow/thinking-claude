# Reasoning Harness — Архитектура надёжной работы с ИИ
*Слой инструкций и модулей поверх Claude. Не «думающая модель» в техническом смысле. Рабочее имя проекта — «Думающий Клод».*

Документ, чтобы (а) через год освежить в памяти, как всё устроено и зачем, и (б) дать постороннему — например разработчику — честно оценить работу. Без воды: что это, как устроено, как проверялось, где слабые места.

---

## 1. Что это

Слой управления контекстом (context-engineering harness) поверх Claude. Идея простая: ценность не в «более умной модели», а в **дисциплине процесса** вокруг задачи. Сам интеллект уже есть в Claude — система лишь организует, *что* и *в каком порядке* в него попадает.

Это **не отдельная модель** и **не reasoning-модель** в техническом смысле (как o1/R1). Это набор инструкций + модулей, работающий поверх любой версии Claude.

## 2. Форма (как собрано)

Три слоя:
1. **Ядро** (`CLAUDE.md`) — всегда-активные принципы и роутер. «Конституция».
2. **Скиллы** (16 модулей) — процедурные режимы, подключаются по необходимости.
3. **Субагенты** — изолированные контексты для параллельного рисёрча и критики.

Ключевое архитектурное правило — **single-writer**: решает и пишет результат всегда один поток; субагенты только читают, исследуют, критикуют. (Вывод из спора двух подходов: Anthropic показала +90% качества на мульти-агентном рисёрче, но Cognition показала, что мульти-агент ломает контекст. Компромисс: один «писатель» + рой «читателей-критиков».)

## 3. Принципы ядра

1. **Не выдумывать.** Не найдено — сказать прямо. Метки типа знания: `[Факт]` (с источником) · `[Вывод]` (из посылок) · `[Предположение]` · `[Не найдено]`.
2. **Честность важнее покладистости.** Если пользователь не прав — спорить аргументами, а не поддакивать.
3. **Value-gate.** Не подключать модуль/рисёрч/роль без реальной пользы. Гейт — молчаливый.
4. **Не хардкодить количество** (ролей, сфер, вариантов) — определять по «эффект × усилия».
5. **Классифицируй, потом маршрутизируй** — распознавать тип задачи на лету, без закрытых списков.
6. **Single-writer** (см. выше).
7. **Гейт перед исполнением — по цене ошибки.** Одобрение обязательно для необратимого, внешне-видимого, высокой ставки, правок ядра/памяти, массовых правок и Форсажа; обратимые локальные шаги внутри согласованной задачи — без переспрашивания (гипотеза H19).
8. **Verifier-first** — потолок качества задаётся тем, насколько результат можно проверить. Есть проверка → гнать качество перебором; нет → выдавать помеченные гипотезы.
9. **Гипотеза — ставка, не факт.** Важные предположения логируются с предсказанием и проверяются практикой; со временем → факт, правка или удаление.
10. **Минимально достаточный контекст и рассуждение, observability, обратимость** — каждому шагу только нужное; больше шагов рассуждения ≠ лучше; ключевые решения фиксируются в журнал; необратимое — через подтверждение.

**Анти-паттерны (чего система избегает):** *Agent theater* — не плодить агентов, если задача решается одним запросом; *Premature architecture* — не строить пайплайн до понимания задачи; *False rigor* — не наращивать этапы проверки, если качество от них не растёт.

## 4. Процесс (для сложных задач)

`Роутер (классификация + value-gate + само-проверка)` → `Цели и Definition of Done` → `План + пре-мортем` → 🚪 `Гейт одобрения` → `Исполнение (single-writer)` → `Критика (red-team)` → `Верификация против DoD` → `Ретроспектива в память`.

Гейт одобрения человеком стоит **между планом и исполнением**: исследование и планирование дёшевы. Объём гейта — по принципу 10: необратимое, внешне-видимое, высокая ставка, правки ядра/памяти, массовые правки, Форсаж. Обратимая локальная работа внутри уже согласованной задачи гейта не требует.

Роутер выбирает **конкретные релевантные модули напрямую** через value-gate. Слой «режимов» (Quick/Deep/Critical/Build) был добавлен, но убран по итогам внешней оценки как *premature architecture* — лишний третий слой маршрутизации. Принцип: сложная задача = нужные модули под задачу, а не все сразу.

### 7.1 Маппинг правило ядра → платформенный механизм (P1-4)

Часть правил ядра описывает словами то, что платформа уже даёт нативным механизмом — не дублировать прозой, использовать механизм:

| Правило ядра | Cowork | Claude Code | Голый чат |

| Независимый проход (принцип 19) | новая сессия/чат вручную | свежий субагент (`Agent`) без истории сборки, опционально другая модель | новый чат вручную |

## 8. Как это проверялось (главное для честной оценки)

Каждый модуль прошёл проверку, а не принят «на веру»:
1. **A/B-тест** (`/test-module`): задача решается дважды — без модуля (A) и с модулем (B) — на 2–3 кейсах, включая «ловушку», где модуль должен сам отказаться (value-gate).
2. **Независимый судья.** Вердикт выносит *отдельная* сессия Claude (Opus), которая модули не строила — чтобы убрать предвзятость автора. (Сработало: судья оказался строже автора, дважды ставил drop-кандидат.)
3. **Реестр гипотез** копит вердикты; решения keep/tweak/drop вносятся в систему.

**Результат:** 16 модулей оставлены (KEEP), 2 (`prioritization`, `benchmark`) выведены в кладбище как дубль базы. Главный честный вывод: многие модули **частично дублируют то, что базовая модель делает сама**; реальная ценность — там, где модуль **ловит то, что база упускает** (`fact-mode` поймал сфабрикованные ссылки; `amplifier` — скрытое допущение, ломающее запуск). Поэтому триггеры узкие.

## 9. Честные ограничения (для критики)

- **Слепое пятно роутера (нашёл внешний рецензент):** классификация задачи — непроверенное LLM-суждение, на котором висит всё, хотя система проповедует verifier-first. Опаснее всего *под-роутинг* — обманчиво-простая задача молча проскакивает мимо fact-mode/ред-тима (над-роутинг хотя бы виден по цене). Смягчено: роутер трактует классификацию как гипотезу и склоняется к проверке при сомнении; fact-mode не гейтится «тривиальностью». Но требует замера матрицы ошибок роутера на реальных задачах.
- **Тесты неглубокие:** n=3 на модуль, оценка по сводкам A/B, не по сырым транскриптам. Это гейт «keep/drop», не строгое измерение.
- **Само-активация базы** конфаундит сравнение: «без модуля» Claude часто уже частично делает то же — ценность ряда модулей это *enforcement*, а не новое поведение.
- **«Весь интеллект уже в Claude»** — система не повышает потолок рассуждений модели, только дисциплинирует процесс.
- **Память файловая**, не «магическая»: работает ровно настолько, насколько ассистент читает/пишет её по инструкции.
- **Кладбище:** `prioritization` и `benchmark` дропнуты как дубль базовой модели (релиз-вычитание). `amplifier` держится на узком триггере (зарытые допущения).
- **Риск переусложнения:** даже 16 модулей легко превратить в оверхед; защита — value-gate и молчаливые гейты, требует дисциплины.
- **Наблюдатель живёт в ядре:** процесс-надзор теперь always-on «Активная оценка» в `CLAUDE.md` (дёшево, каждый ход), а не отдельный периодический скилл. Overseer удалён (v1.3.0) как устаревший.

## 11. Уже разобранная обратная связь (для новых рецензентов)

Чтобы отзывы не повторялись — вот что внешние оценки уже подняли и чем это закрыто.

**Принято и внедрено:**
- *Слепое пятно роутера* (роутер — непроверенное LLM-суждение; опаснее всего молчаливый под-роутинг) → роутер трактует классификацию как гипотезу и склоняется к проверке при сомнении; `fact-mode` не гейтится «тривиальностью».
- *Режимы* (Quick/Deep/Critical/Build) добавлены, затем **убраны** как premature architecture (внешняя оценка №2) — роутер выбирает модули напрямую через value-gate.
- *Анти-паттерны* (agent theater / premature architecture / false rigor) → в ядре.
- *Минимально достаточное рассуждение* («больше шагов ≠ лучше») → принцип в ядре.
- *Название оверселлит* → переименовано в **Reasoning Harness**.

**Рассмотрено и отклонено — просьба не предлагать заново (с обоснованием):**
- *Числовая шкала сложности* («6/10 → architect+verification») — хардкод и pseudo-precision (тот самый анти-паттерн *false rigor*), противоречит принципу «не фиксировать количество». Суть уже покрыта value-gate.
- *Процентный ROI-ledger по модулям* («помог 35/100, +12%») — неизмеримо для открытых доменов: нет автоматического судьи на каждое использование. Эволюция модулей уже идёт через A/B + реестр гипотез.

**Открытые вопросы — сюда критика особенно полезна:**
- Главная ось роадмапа — **вычитание**: критерий «переживёт ли модуль более сильную модель». Релиз-вычитание начат (2 модуля в кладбище).
- Тесты модулей: n=3, оценка по сводкам A/B, не по сырым транскриптам.
- Overlap `amplifier`↔`pre-mortem`/`red-team` — **снят** разведением по «фаза×объект».
- Рост ядра: в какой-то момент консолидация важнее добавления (следующий шаг, вероятно, на вычитание).
