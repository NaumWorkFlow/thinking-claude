# Верификация / Definition-of-Done (M14)

Назначение: подтвердить, что сделанное соответствует тому, что требовалось — прежде чем считать задачу закрытой.

## Когда включаться
По завершении блока/задачи, перед тем как отдать результат. Особенно — если работа шла долго или без присмотра.

## Отличие от red-team
- `red-team` ищет *слабые места* (что можно сломать).
- `verification` подтверждает *готовность* (соответствует ли результат критериям). Разные шаги; verification — финальный гейт.

## Процедура
1. **Подними критерии** из Фазы 1 (Definition of Done, ограничения). Нет зафиксированных критериев — честно скажи и выведи их из задачи.
2. **Первый вопрос: чем это можно ВЫПОЛНИТЬ, а не обдумать?** Проверь по типу результата (желательно свежим взглядом / в отдельном контексте):
   - **Код** → тесты, прогон, проверка крайних случаев.
   - **Факты/числа/цитаты** → сверка с источниками через `fact-mode`.
   - **Текст/документ/план** → чек-лист приёмки по каждому критерию.
3. **Отчёт:** по каждому критерию — выполнено / не выполнено / частично, с конкретикой. Не сглаживай.
4. Если есть пробелы — верни на доработку (Фаза 4), не закрывай задачу.

## Регламент независимого прохода (принцип 19)

На высокоставочных / само-оценочных решениях (keep/drop модуля, финальный вердикт, оценка своей же работы) — не суди сам. Операционализация:
1. **Свежий субагент** — без истории сборки/авторства, не видел, как строился артефакт.
2. **Вслепую** — подавай артефакт на оценку без пометок «это моё» и без хода рассуждений, которые к нему привели.
3. **Фиксированная рубрика** — критерии заданы заранее, не придуманы постфактум под результат.
4. **На высоких ставках — другая модель**, чем писавшая.

Статус: гипотеза H14 в `memory/HYPOTHESIS-LEDGER.md` — этот регламент не заменяет ручную отдельную сессию-судью, пока `/test-module` не подтвердит, что он не хуже.

## Выход
Таблица «критерий → статус → комментарий» + вердикт: готово / на доработку (что именно).

## Не делай
- Не подтверждай «готово» при незакрытых критериях или падающих тестах.
- Не подменяй проверку критикой и наоборот.
- **Не чини сам** (не переписывай код/план) — верификатор фиксирует разрыв с DoD, а чинит писатель/архитектор (single-writer). Можешь указать *что* не так, но не выдавай готовый фикс.
- Нет заданного DoD — не проверяй молча против самопридуманного: пометь «DoD не задан», предложи выведенные критерии и подтверди с пользователем (анти-круговая-проверка).
