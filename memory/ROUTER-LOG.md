# Лог решений роутера

> Механизм для сбора матрицы ошибок роутера (был заявлен в реестре гипотез H11/H13, но не существовал как файл — см. `FABLE5-REVIEW.md` P1-2; сам этот файл в репозитории **не сохранён**, ссылка историческая). Пишется **только** для нетривиальных/сомнительных решений роутера (value-gate на сам лог — не логировать каждый тривиальный запрос, иначе лог сам станет оверхедом).

## Когда писать строку

Запись привязана к **детерминированным точкам**, а не к самоощущению «я засомневался» — субъективный триггер не срабатывал (лог простоял пустым с 02.07 по 27.07.2026).

Строка пишется обязательно:
- в конце каждого прогона `/max` (Шаг 4 команды) — независимо от того, сомневался роутер или нет;
- в конце `/test-module` (Шаг 5) и `/harness-probe`;
- дополнительно — в Фазе 7 любой задачи, если задним числом видно, что классификация была неточной.

**Честная оговорка о выборке.** Такой лог покрывает форсажные и тестовые прогоны, а не поток обычных задач — выборка смещена в сторону сложных. Матрицу ошибок роутера по ней можно строить только для этого класса задач; для повседневного потока роутер остаётся неизмеренным (см. H11).

## Формат строки
`ДАТА · запрос (≤5 слов) · класс (тривиальный/средний/комплексный) · подключённые модули · ретроспективно верно? (да/под-роутинг/над-роутинг) · гейт (был / не требовался / пропущен зря)`

## Как читать (в `/harness-maintenance`)
Матрица ошибок: сколько строк — «под-роутинг» (приоритетный сигнал, он молчалив по умолчанию) против «над-роутинг» (виден по цене, менее срочен). Паттерн — предложи правку триггера конкретного модуля/роутера в `HYPOTHESIS-LEDGER.md`, не молчаливо переписывай `CLAUDE.md`.
